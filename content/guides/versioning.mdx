# Versioning

CamelMind supports shipping multiple versions of your documentation from a single project. Each version has its own navigation file and can have entirely different content and structure.

## versions.yml

The version registry lives at `versions.yml` (configurable via `versionsFile` in `camelmind.config.ts`):

```yaml
versions:
  - id: "latest"
    label: "Latest"
    stable: true
    nav: nav/nav.yml
```

### Version fields

| Field | Required | Description |
|---|---|---|
| `id` | Yes | URL prefix for this version (e.g., `v2` → `/v2/...`) |
| `label` | Yes | Display name shown in the version selector dropdown |
| `stable` | Yes | `true` for stable releases; `false` for pre-release |
| `nav` | Yes | Path to this version's `nav.yml` file |
| `badge` | No | Short badge text displayed next to the label (e.g., `"Beta"`) |

## Adding a new version

<Steps>
<Step n={1} title="Create a nav file for the new version">

Copy your existing nav and adjust as needed:

```bash
cp nav/nav.yml nav/nav-v2.yml
```

</Step>
<Step n={2} title="Register the version in versions.yml">

```yaml
versions:
  - id: "v2"
    label: "v2 (Latest)"
    stable: true
    nav: nav/nav-v2.yml
  - id: "v1"
    label: "v1"
    stable: true
    nav: nav/nav-v1.yml
  - id: "dev"
    label: "dev"
    stable: false
    badge: "Beta"
    nav: nav/nav-dev.yml
```

</Step>
<Step n={3} title="Add version-specific content (optional)">

You can version content files by placing them in a version-prefixed folder:

```text
content/
├── getting-started/          # shared content
│   └── introduction.mdx
└── v1/                       # v1-specific overrides
    └── getting-started/
        └── introduction.mdx
```

Then point the v1 nav file at the versioned path:

```yaml
# nav/nav-v1.yml
nav:
  - label: "Getting Started"
    dropdown: true
    items:
      - label: "Overview"
        slug: /getting-started/overview
        file: content/v1/getting-started/overview.mdx
        roles: []
```

</Step>
</Steps>

## How versioned URLs work

CamelMind automatically prefixes all slugs in a versioned nav with the version `id`. You write:

```yaml
slug: /getting-started/overview
```

And the site serves it at `/v2/getting-started/overview`. The unversioned nav (the first entry in `versions.yml`) is served at the root path `/getting-started/overview`.

<Callout type="note">
The version selector in the top nav preserves the current page path when switching versions. If the equivalent slug doesn't exist in the target version, it redirects to the home page.
</Callout>

## Version selector UI

The version selector renders automatically in the top nav whenever two or more versions are defined in `versions.yml`. It shows:
- Each version's `label`
- The `badge` text for unstable versions
- A download icon (for offline builds, if enabled)

## The "latest" convention

By convention, the first entry in `versions.yml` is the canonical "current" version. Its `id` can be anything — using `"latest"` means the root URL (`/`) serves that nav, while a named ID like `"v2"` would only serve it at `/v2/...`.

Using `"latest"` as the id of your current version is recommended so stable URLs don't contain a version number that becomes stale.

## Stable vs unstable versions

Set `stable: false` on pre-release versions. This:
- Shows the `badge` label in the version selector
- Allows offline download to be restricted to stable versions only (in the download endpoint)

<Callout type="warning">
Users can still navigate directly to unstable version URLs. Stable/unstable is a UI hint, not an access control. Use `roles` on nav entries for access control.
</Callout>
